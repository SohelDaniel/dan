# Audit A2: axiom 2, Structure

"Shared baselines and scales, fixed for the whole script by a prescan; they never jump." (HANDOFF §3)
"Bars share a zero baseline. Scales are per property and never jump mid-script, because the whole script is
pre-scanned." (README, Axioms enforced)

Auditor A2. Repo read-only; nothing built. Everything I wrote is under this folder:
`scenes/` (every reproducer), `shots/` (PNG frames and contact sheets `sheetA..J.png`), `out/` (readbacks, reports).
All commands run from the repo root; `$S` = this folder's `scenes/`.

Headline. The prescan does exactly what the axiom says for **literal** values in a **whole** script: baselines, bar
scales, axis/number-line/timeline ranges and 3D boxes are right from the first frame and never move (r2-whole, r3-whole,
r6, r10b, r13-whole). It fails in three places, all real:
1. **Anything the prescan cannot read.** `see()` records only `Value::NUM` (engine.cpp:120-129). An `{expr}` value,
   a `param` the learner drags, and an expression with no literal anywhere are invisible to it. Bars then slide their
   shared scale every frame (r1); a bar whose value is only ever an expression sits at full height no matter what it
   is worth (r16, a **real chat turn**: "the pull drops to a quarter" while the bar ends at the height it started);
   dots on inferred axes and points in a space box run off the picture (r3c, r10).
2. **The live mode.** Each appended chunk re-runs the prescan over the text so far (engine.cpp:89), so the scale is
   "fixed for the whole script" only up to the chunk that has arrived. A later chunk with a larger value re-scales
   what is already on stage: bars ease to a quarter height (r2), inferred axes glide from 0-2 to 0-14 (r3), a
   timeline from 1990-2000 to 1990-2020 (r13), dot radii **jump** (r4, no easing), and the scene's auto schema flips
   `free -> axes` or `axes -> space` (r5, r5b). The final readback is identical to the whole-script run in every case
   (`append.sh`'s property holds), which is exactly why no test catches any of this.
3. **The checker is blind to 1.** `--check` plays instantly: `update()` executes every step while nothing blocks
   (engine.cpp:1412-1428) and nothing blocks in instant mode, so the first `layout()` (1468) sees the end state and
   ranges initialise from it. `--layout-report` (a real-time play) scores r3c and r10 at 84 with "runs 4673px off the
   screen"; `--check` scores both 100 with no message. The server feeds Claude `--check`'s lints, not the report's.

Two smaller structural findings: the prescan is keyed by property **name across all kinds and all views**, so an
invisible `param value=50` sets the visible bars' scale (r1c) and one view's inferred axes stretch to another view's
values (r8, with a false `zero:` lint); and the plot's pixel scale changes mid-sentence when a formula arrives,
although the prescan counted the formulas (r9).

## 2. Rule vs code gaps

1. README "Scales ... never jump mid-script, because the whole script is pre-scanned" (README.md:363) and the dictionary "one scale per property, fixed by pre-scanning every value the script ever uses" (README.md:350). Code: `see()` records only `v.type == Value::NUM` (engine.cpp:120-121); `{expr}` is `Value::EXPR` (script.hpp:27) and is never evaluated by the prescan; `layoutFree` then widens the extent from the live value each frame (layout.cpp:1025-1026 `std::max({0.0, maxVal_..., v})`) and eases the scale to it (1066-1069). "Every value the script ever uses" is "every literal the script writes".
2. HANDOFF §3 "fixed for the whole script by a prescan". Code in live mode: `appendText` -> `analyze(false)` -> `usePrescan()` (engine.cpp:89, 224, 291-295) replaces the extents on every chunk; `autoSchema_` too (223). The prescan is of the script so far. Nothing in README, HANDOFF or prompt says the live mode is weaker, and the chat is the live mode.
3. The map's own comment in the code: layout.cpp:1013 "bars: a shared zero, one scale per property" and 1060-1072 "a changing scale moves smoothly, never snaps" (barScale eased). The axiom says scales never change; the code's design is "if they change, ease". Those are different promises; the second one is what is implemented, and it is undocumented in the README.
4. space.cpp:371-372 "worked out when things are added and eased there (a scale never jumps)" and layout.cpp:63-75 `dotRadius`: `maxAbs_[k]` used raw. The comment's rule is broken by the dot radius (a jump) when `maxAbs_` changes under a live append.
5. README.md:157 "Give ranges that hold everything (a thing that leaves the box is linted)" and the lint at space.cpp:531. Code: the lint runs inside `layoutSpace` per frame (space.cpp:521-540), so (a) it fires once per frame while the thing moves (100 times in r10) and (b) never under `--check`, because instant mode lays out the end state only, whose box includes the final position. The server's `<last_scene_issues>` comes from `--check` (chat/server.mjs:234-239, 434), so Claude is never told.
6. main.cpp:176-180 `--check` ("Decodability: the final scene ... must give the same scene") and HANDOFF §2 "`--check` ... lints + score". Code: in instant mode `update()` executes all steps before the one `layout()` (engine.cpp:1412-1428, 1468); ranges, baselines and the band are therefore computed from the end state. The check's layout score is the score of a picture no learner sees for scenes with motion (r3c: check 100, real-time 84).
7. engine.cpp:143-150 "the auto schema per scene from structure" with the comment "boxes are graph things from the first one, so links or numbers arriving later don't re-lay the scene": the same protection is missing for `path`/`fn` arriving after bars (free -> axes) and for `z=` arriving after a 2D point (axes -> space).
8. README dictionary "magnitude: bar length / dot area, from a shared zero": the prescan key is the property name across kinds, so a `param`'s `value` (an "invisible number that drives others", README.md:75) and a `label`'s `value` enter the bars' scale (engine.cpp:158-160 has no kind filter in `see()`, though 166 excludes `label`/`param` from `hasMag`).
9. HANDOFF §4 "Stage {40,66,1200,494}" and "Layout per frame: ranges, then the band, then the schema layout": the band is laid out before the schema every frame, and `bandNeed_` grows as blocks arrive (layout.cpp:639), so the plot's area is a function of time even in a whole script whose blocks the prescan counted (engine.cpp:144 `sceneBlocks_`).

## 3. Where this axiom limits creative freedom

- **Geology / history: 4.5 billion years, then the last 10,000.** `scenes/r14-geology-camera.dan`: a `timeline` with Earth forms, first life, dinosaurs end, farming, now, then `camera on=d zoom=100000`. `--check`: `camera: line 10 needs an axes or plane scene (this one is timeline)`; the frame (sheetI top) shows farming and now on one dot and tick labels with float garbage ("-4499999744", now = "256"). The axiom forbids re-scaling the line; the sanctioned move (the camera, "zoom is a pointer", camera.cpp:1-8) exists only for `axes`/`plane` (camera.cpp:19). So this lesson cannot be told on a timeline at all today; the workaround is `axes` with years on x and `camera zoom`, which loses the timeline's event labels. (HANDOFF §9 lists "no camera pan for long arrays or timelines" as small; for history and geology it is the whole lesson.)
- **Economics: a series whose last point dwarfs the rest.** `scenes/r15-gdp.dan` (world GDP per person, 1 AD to 2020, sheet `shots/r15_end.png`): on the honest fixed scale the first four points are one flat line on the floor and the story ("nothing for eighteen centuries, then this") is told by the voice alone. There is no log axis (no `log` anywhere in README/prompt/toolbox), and the axiom rightly forbids rescaling y mid-script. The camera can zoom into y in [0,1000] and back out, which is the 3Blue1Brown way, but Claude writes no camera moves in the 63 real turns. Related weak topics in the eval (pH, decibels, Richter, Moore's law, compound interest) are all exponential; a `y=log` option on `axes` would be one structure, fixed for the script, that fits them.
- **Streamed data that grows: a cumulative total, a tally, a running maximum.** r2/r13 are the pattern: the first beat shows small values, a later beat a large one, and in the chat the stage re-scales on arrival. Writing the range in the first turn needs the author to know the end of the lesson; Claude does this for plots (33/33 carry ranges) but has no way to do it for `free` bars except `max=`, which it has never written (0/63). An economics "then the pandemic year" chart, a sports "then Bolt" bar, a biology "then the blue whale" dot all re-scale the earlier picture under the learner.
- **Physics with derived quantities.** r16 (the real Gravity turn) is the honest way to write Newton: the pull is `{m1*m2/d^2}`, not a typed number. The axiom's mechanism (literals) cannot see it, so the one bar that carries the lesson's claim is the one bar that cannot show it. `max=` would fix it only if Claude knows the maximum of an expression it wrote not to have to compute.
- **Two views of one property.** r8: a signal and its zoomed-in detail, a city map and a country map, a cell and a tissue, all want the same property name at two scales; today the inferred ranges are shared across views, so the small view inherits the big one's extent (and a false `zero:` coincide lint). Explicit ranges avoid it, at the cost of the lookahead.

## 4. Small model

Measured against `reports/Small model for tutor weak spots.md` (its rule: code first; a small model only for a narrow, label-rich, checkable job; never a scene writer):

- **Predicting ranges / `max=` ahead of a live scene** (the "lookahead" a human author does). Labels exist for free: every finished turn's readback gives the true extent per property (`# derived max/min`), and `live.dan` holds the order in which beats arrived, so (first beat -> final extents) pairs exist for all 63 turns and for every eval scene. Checkable: compare with the whole-turn prescan after the fact; a wrong guess costs a margin, not a wrong picture. **Not worth it**: the frontier model already writes ranges on 100% of real plots, and the remaining gap (expression-driven values, live widening) is deterministic: the shadow engine already evaluates every value ahead of the voice (engine.hpp:530-533). Fix 1 below gets the same lookahead from code, exactly, for the script that exists; no model can know the next turn either.
- **Choosing a scale type** (linear vs log, absolute vs per-capita, shared vs separate scales across views). A judgement job with no labels and a frontier-model plan step that already decides the picture. No.
- **A scale-change spotter for evals** ("did anything on stage change size without a data reason?"). Pure code: the engine knows its own `barScale_`, `axX0_...`, `maxAbs_`, `bandH_` and can log them in `--layout-report` (fix 5's test does this). No model.
- The report's one candidate, a binding-repair tagger, touches this axiom only by inserting labels; irrelevant here.

Conclusion for axiom 2: no job for a small model. The labels that exist are better spent on fix 1 and on a lint that teaches the frontier model where its lookahead matters.
